# 🚆 RZD Tickets Bot

[English](README.md) | **Русский**

Telegram-бот для поиска билетов РЖД, который умеет отслеживать
конкретный поезд и класс вагона и присылать уведомление в момент
появления мест — включая отдельный фильтр мест, разрешённых для
перевозки небольших питомцев.

**Стек:** Python · [aiogram 3](https://docs.aiogram.dev/) · Playwright ·
SQLite · APScheduler

## Что умеет

- **`/search`** — пошаговый диалог с автодополнением: город отправления,
  город прибытия, дата. В ответ — все поезда на маршруте с числом мест,
  ценами и разбивкой по нижним/верхним полкам для каждого класса вагона.
- **Отслеживание мест** — нажмите на класс вагона под любым поездом,
  чтобы поставить его на отслеживание. Бот опрашивает РЖД в фоне и
  пишет, как только число мест увеличилось (например, кто-то сдал
  билет на поезд, где раньше всё было распродано). Отслеживание — по
  конкретному классу («Купе», «Плацкарт»), а не просто «любое место на
  этом поезде».
- **🐾 Места для питомцев** — РЖД отдельно помечает места, выделенные
  для пассажиров с небольшими животными. Бот показывает их как
  отдельный вариант для отслеживания, не путая с обычными местами того
  же класса.
- **`/mytracking`** — список активных отслеживаний с возможностью
  остановить любое из них.
- **Прямая ссылка на покупку** — каждый результат поиска ведёт на
  соответствующую страницу `ticket.rzd.ru`, чтобы саму покупку вы
  завершали на официальном сайте РЖД (бот только ищет и отслеживает —
  он никогда не работает с оплатой или данными пассажиров).
- **Ограничение доступа** — опциональный список разрешённых Telegram
  user id, чтобы бот, запущенный для своей семьи, не был открыт всему
  интернету.

## Самое интересное: как вообще получить данные с ticket.rzd.ru

У РЖД нет публичного API, а сайт активно защищён от автоматических
запросов — так что проект получился не «вызвать готовый REST-эндпоинт»,
а небольшое упражнение в реверс-инжиниринге:

1. **Обычные HTTP-клиенты тихо блокируются.** Запросы `httpx`/`requests`
   к `ticket.rzd.ru` возвращают `200 OK` с *пустым телом* — без ошибки,
   просто ничего. Причина — [BotFaqtor](https://botfaqtor.ru/),
   коммерческий антибот-сервис, подключённый на странице
   (`cdn.botfaqtor.ru/one.js`), который снимает отпечаток клиента и
   тихо отбрасывает запросы, не похожие на настоящий браузер.
2. **Настоящий (пусть и headless) браузер проходит.** Управление
   реальным Chromium через Playwright — даже в headless-режиме —
   проходит проверки BotFaqtor, потому что это действительно браузерный
   движок. Все запросы выполняются через `fetch()` **внутри** уже
   открытой страницы `ticket.rzd.ru`, а не через отдельный
   `APIRequestContext` Playwright — у них разный сетевой стек, и
   `APIRequestContext` оказался ненадёжен (ошибки резолва DNS) на
   одной из тестовых машин, где `fetch()` на странице работал без
   проблем.
3. **Поиск настоящего источника данных.** Первая рабочая версия
   парсила DOM уже отрисованной страницы результатов поиска. Но
   наблюдение за вкладкой Network при обычном поиске на сайте показало
   настоящий бэкенд-эндпоинт, который использует сама страница —
   `/api/v1/railway-service/prices/train-pricing` — один JSON-ответ с
   гораздо большей детализацией, чем показывает интерфейс (число
   нижних/верхних полок по каждому классу, флаг `HasPlacesNearPets` на
   каждую группу вагонов, точные цены). Переход на него сократил поиск
   с ~15–20 секунд ожидания отрисовки DOM до пары секунд и вообще
   сделал возможным отслеживание по классам вагона (включая фильтр
   мест для питомцев) — такая детализация просто не доходит до
   отрисованной страницы.
4. **Сертификаты.** Сертификат `ticket.rzd.ru` выпущен российским
   государственным CA, которого нет в большинстве доверенных хранилищ
   по умолчанию — поэтому все HTTP-клиенты в проекте явно отключают
   проверку сертификата именно для этого хоста.

Официальной документации на всё это нигде нет — интеграция в
[`bot/rzd_api.py`](bot/rzd_api.py) целиком построена по наблюдению за
реальным сетевым трафиком и потребует доработки, если РЖД изменит сайт.

## Структура проекта

```
bot/
  rzd_api.py       — Playwright-клиент к ticket.rzd.ru (станции, поиск поездов)
  db.py            — SQLite: хранение активных отслеживаний
  scheduler.py     — фоновая задача повторной проверки отслеживаемых поездов
  middlewares.py   — список разрешённых пользователей Telegram
  formatting.py    — форматирование сообщений о поездах и местах
  keyboards.py     — инлайн-клавиатуры (выбор класса, ссылка на покупку, остановка)
  states.py        — состояния FSM aiogram для /search
  utils.py         — разбор и форматирование дат
  config.py        — переменные окружения
  handlers/
    common.py      — /start, /help, /cancel
    search.py       — диалог /search
    tracking.py     — постановка на отслеживание, /mytracking
  main.py          — точка входа (запускает браузер, бота и планировщик)
```

## Установка

```bash
git clone https://github.com/Lelena1/rzd-tickets-bot
cd rzd-tickets-bot
python -m venv .venv
.venv\Scripts\activate   # Windows
pip install -r requirements.txt
python -m playwright install chromium
copy .env.example .env   # вписать токен бота от @BotFather
```

## Запуск

```bash
python -m bot.main
```

## Известные ограничения

- **Не мгновенно.** Каждый поиск — это настоящая загрузка страницы/
  запрос к API через браузер (пара секунд), а не мгновенный кэшированный
  ответ — нормально для личного использования, но не рассчитано на
  большой поток запросов.
- **Привязка к текущему виду сайта.** Названия полей и единственный
  оставшийся CSS-селектор — это снимок `ticket.rzd.ru` на сегодняшний
  день; при редизайне сайта потребуется обновить `bot/rzd_api.py`.
- **Нет гарантии обхода защиты.** Трафик headless-но-настоящего браузера
  сегодня проходит проверки BotFaqtor, но антибот-сервисы постоянно
  развиваются — это не постоянное решение.
- Состояние FSM хранится в памяти (`MemoryStorage` aiogram) — диалог
  `/search` в процессе прерывается при перезапуске, но сохранённые
  отслеживания (в SQLite) переживают его.
- Отслеживание срабатывает при *увеличении* числа мест относительно
  последней проверки (в т.ч. с 0 до N), а не при каждой проверке, где
  места есть — чтобы не слать одно и то же уведомление каждые 5 минут.
